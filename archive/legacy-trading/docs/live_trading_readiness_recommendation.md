# 示例小额预算 实盘实验账户接入建议

生成时间：2026-06-16 15:22:51 CST

## 结论

当前系统可以考虑进入 **示例小额预算 子账户的小资金实盘实验准备阶段**，但不建议在未补齐实盘硬停止机制前直接开放真实自动下单。

推荐路径是：

1. 继续使用真实市场数据、资金费率和交易所 API 做 paper / readonly 验证。
2. 先补齐实盘级硬停止：持久化 emergency、禁止新开仓、只允许减仓/平仓、Telegram 关键告警、人工恢复。
3. 硬停止测试通过后，再用 示例小额预算 子账户做极小资金灰度。

这不是对策略稳定盈利的确认，而是一个受控实验流程。

## 三类亏损控制的含义

### 1. 单笔最大损失预算

`max_single_trade_loss_pct: 0.006` 的含义不是“浮亏超过 0.6 USDT 才临时止损”，而是：

> 开仓前就根据止损距离、账户权益、仓位和杠杆计算，使这笔交易在理论止损被打到时，亏损大约不超过账户权益的 0.6%。

以 示例小额预算 账户为例：

- 单笔风险预算：`100 * 0.006 = 0.6 USDT`
- 如果技术止损距离是 2%，则最大名义仓位约为：
  - `0.6 / 0.02 = 30 USDT`
- 如果使用 10x 杠杆，则保证金约为：
  - `30 / 10 = 3 USDT`

所以单笔最大损失预算控制的是：

> 一笔交易判断错了，止损被打时，理论上最多亏多少账户本金。

实盘中由于滑点、手续费、资金费率和撮合延迟，实际亏损可能略高，因此需要留缓冲。

### 2. 单日最大亏损

`max_daily_loss_pct: 0.03` 的含义是：

> 当天累计亏损达到约 3% 后，系统停止当日新开仓。

以 示例小额预算 账户为例：

- 单日亏损达到约 3 USDT 后，应停止新开仓。
- 目的不是永久停止交易，而是防止同一天内连续错误信号反复扣血。

建议触发后行为：

- 禁止新开仓。
- 保留必要的减仓/平仓能力。
- Telegram 推送硬停止告警。
- 是否次日恢复，应至少通知人工确认；不要悄悄自动恢复。

### 3. 总回撤硬停止

`max_drawdown_pct: 0.08` 的含义不是“账户亏 8 USDT 后从此永远不能交易”，而是：

> 当账户从权益高点回撤达到约 8% 后，自动交易进入 emergency / paused 状态，停止新开仓，必须人工复盘后才能恢复。

以 示例小额预算 账户为例：

- 初始权益：示例小额预算
- 如果账户先涨到 105 USDT
- 后面跌到 96.6 USDT
- 从高点 105 回撤到 96.6，回撤约 8.4 USDT
- 应触发账户级熔断

触发后建议行为：

- 自动进入 emergency。
- 禁止所有新开仓。
- 只允许减仓或平仓。
- Telegram 推送告警。
- 需要人工检查策略、行情状态、API 状态、重复下单风险和风控执行情况。
- 人工确认后才能恢复。

一句话区分：

- 单笔最大损失预算：控制“一笔错了最多亏多少”。
- 单日最大亏损：控制“一天错了最多亏多少”。
- 总回撤硬停止：控制“整个实验是否已经跑偏，需要停下来检查”。

## 当前还缺的实盘级硬停止能力

当前风控代码已经能在触发亏损限制时返回 `hold`，但这还不等于完整实盘硬停止。

实盘硬停止至少需要以下能力：

### 1. 持久化 emergency 状态

触发以下任一条件时，系统应写入运行状态文件，例如：

```yaml
mode: "emergency"
global_paused: true
emergency: true
```

触发条件包括：

- 单日亏损达到上限。
- 总回撤达到上限。
- 连续亏损达到上限。
- 交易所状态异常。
- 数据状态异常。
- 账户状态与交易所真实状态不一致。

不能只是在当前一轮风控评估里返回 `hold`，否则下一轮或其他路径仍可能继续尝试开仓。

### 2. 禁止所有新开仓

进入 emergency 后，不管策略信号、社媒信号、AI 分析或趋势信号如何，都必须禁止新开仓。

### 3. 只允许减仓或平仓

实盘模式下 emergency 状态应只允许：

- close
- reduce-only
- cancel open orders

不允许：

- open long
- open short
- reverse position
- increase position

### 4. 人工恢复

触发硬停止后，不应自动恢复。

恢复应要求人工确认，例如：

- 手动修改 runtime state。
- 或通过受控 Telegram 命令 `/resume ALL`。

恢复前应复盘：

- 是否策略失效。
- 是否市场状态切换。
- 是否 API 异常。
- 是否发生重复下单。
- 是否仓位状态与交易所状态不一致。

### 5. 关键事件告警

Telegram 不应推送普通 hold 心跳，但必须推送硬停止事件：

- 单日亏损触发。
- 总回撤触发。
- 连续亏损触发。
- exchange/data unhealthy。
- 账户状态 reconcile 失败。
- 订单失败超过重试上限。
- emergency 进入和人工恢复。

## 建议的 示例小额预算 实盘灰度规则

### 初始灰度范围

建议第一阶段只启用高流动性币种：

- BTCUSDT
- ETHUSDT

暂不建议一开始启用全部山寨币实盘交易，因为山寨币滑点、波动和插针更容易放大小账户风险。

### 风控阈值建议

在不默认降低动态杠杆的前提下，建议保留或微调如下：

- 单笔最大理论亏损：约 0.6 USDT
  - `max_single_trade_loss_pct: 0.006`
- 单日最大亏损：约 3 USDT
  - `max_daily_loss_pct: 0.03`
- 账户级总回撤熔断：约 8 USDT
  - `max_drawdown_pct: 0.08`
- 连续亏损停止：建议从 4 次改为 3 次用于实盘实验
  - 当前：`max_consecutive_losses: 4`
  - 建议实盘实验：`max_consecutive_losses: 3`
- 最大同时持仓：2
  - `max_open_positions: 2`
- 同方向最大持仓：1
  - `max_same_direction_positions: 1`

说明：

- 不建议把“降低杠杆”作为默认保守化手段。
- 更重要的是提高入场质量、过滤条件、冷却机制、相对强弱判断和社媒信号权重。
- 杠杆可以继续由动态风控控制，但硬停止必须可靠。

## 实盘接入分阶段计划

### 阶段 0：继续 paper + readonly 验证

目标：确认真实数据链路稳定。

检查项：

- 行情价格正常。
- 资金费率正常。
- 交易所健康状态正常。
- 合约规格、最小下单量、价格精度、数量精度可读取。
- API 失败次数可监控。
- paper 账户状态与事件日志一致。

### 阶段 1：补齐硬停止

必须实现并测试：

- 达到单日亏损上限后，写入 emergency。
- 达到总回撤上限后，写入 emergency。
- 达到连续亏损上限后，写入 emergency。
- emergency 后禁止所有新开仓。
- emergency 后只允许减仓/平仓。
- 触发硬停止后发送 Telegram 关键告警。
- 恢复必须人工操作。

建议新增测试：

- `test_daily_loss_triggers_persistent_emergency`
- `test_drawdown_triggers_persistent_emergency`
- `test_consecutive_losses_triggers_persistent_emergency`
- `test_emergency_blocks_new_entries`
- `test_emergency_allows_reduce_only`
- `test_hard_stop_notification_is_actionable_only`

### 阶段 2：交易所状态 reconcile

实盘前必须确认：

- 本地状态和交易所真实持仓一致。
- 本地未成交订单和交易所未成交订单一致。
- 异常情况下先 cancel open orders，再禁止新开仓。
- 状态不一致时进入 emergency，而不是继续交易。

### 阶段 3：示例小额预算 子账户小资金灰度

初期规则：

- 只启用 BTCUSDT / ETHUSDT。
- 保持最大同时持仓不超过 2。
- 保持同方向最多 1 个仓位。
- 单日亏损 3 USDT 熔断。
- 总回撤 8 USDT 熔断。
- 连续亏损 3 次熔断。
- 所有实盘成交和持仓变化必须 Telegram 通知。
- 普通 hold 不通知。

观察周期：

- 至少 3-7 天。
- 更稳妥是累计 50 笔以上闭环交易后再评估是否扩大范围。

### 阶段 4：扩大实盘范围的条件

只有满足以下条件，才考虑扩大币种或交易频率：

- 没有触发硬停止。
- 没有状态不一致。
- 没有重复下单。
- 没有 API 异常导致错误交易。
- 真实成交滑点和手续费在可接受范围内。
- 多单和空单表现没有明显单边失衡。
- 盈利不是只来自单一行情阶段。

## 当前不建议直接做的事

- 不建议未补齐硬停止前直接开启 live 自动下单。
- 不建议因为最近 paper 盈利就扩大仓位。
- 不建议一开始启用全部币种实盘交易。
- 不建议触发亏损熔断后自动恢复。
- 不建议只依赖风控返回 `hold`，而不写入持久化 emergency。
- 不建议把 paper 账户状态和 live 账户状态混用。

## 最终建议

对 示例小额预算 实验子账户，实盘不是完全不能做，但应该按实验系统处理，而不是按成熟交易系统处理。

当前最合理的判断是：

> 可以准备小资金实盘灰度，但必须先实现实盘硬停止。硬停止通过测试后，再允许 示例小额预算 子账户以 BTC/ETH 为主进行受控实盘实验。

核心原则：

- 允许小资金试错。
- 不允许系统失控。
- 单笔亏损可接受。
- 单日连续错必须停。
- 总体跑偏必须人工复盘。
- 任何状态不一致都优先保护本金，而不是继续交易。
