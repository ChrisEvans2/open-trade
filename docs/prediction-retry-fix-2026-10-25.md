# 预测任务失败与重试冲突修复

日期：2026-10-25（Asia/Shanghai）；仓库 `/srv/open-trade`。本轮针对用户要求修复预测任务本身，沿用已恢复的Codex登录连接，不再以通知关闭作为任务修复证据。

## 用户需要知道的原因

用于一次分析的行情快照，与一份1h/4h/6h/12h预测的有效期限，是两个不同概念。本次180秒限制约束的是启动/提交分析时的行情快照，不表示所有趋势预测180秒后结束。

已确认的技术问题：

1. **重试时间互相冲突。** 输入快照最多180秒；启动前需留出120秒总分析预算与20秒准备预算。因此超过40秒的旧输入已不适合再次启动。但原失败路径固定至少等待60秒，再重试同一个有冻结输入的任务，必然被过期校验拒绝。根因可能是模型超时、格式错误或证据引用错误，任务最后却只显示CONTEXT_EXPIRED。
2. **真实提交错误被掩盖。** 模型可能提交不合契约的字段、错误证据ID、非冻结边界/容差或位于触发价错误一侧的目标。这些报告应被拒绝；原执行器看到“没有正式预测落库”，统一归成AGENT_NO_FORMAL_RESULT，丢掉了为什么没发布的具体线索。模型收到的提示也过于笼统，纠正需要多轮，进一步消耗时限。
3. **上下文的变化判断有多余触发。** 持仓仅更新监测游标/更新时间，也可能改变父综合的版本摘要；分钟行情正在补齐时就启动综合，会暂时漏掉子预测，补齐后子集合又变化，使刚做的分析作废。真正的持仓变化、预测失效和缺失数据仍必须严格处理。
4. **旧队列与优先级导致重复工作和等待。** 旧版本已经留下同周期多条排队请求，新的入队合并只能防止新重复，不能自动识别旧请求；父综合固定优先又使一些需要更新的子周期等待超过半小时，父综合持续缺少新子预测。
5. **已平仓记录的展示存在歧义。** 历史CLOSED记录仍作为position对象交给模型，而正式决策要求空仓时position_id为null。新输入现在只把OPEN记录呈现为当前持仓，保留原历史账本及版本校验。

上轮网络403修复只恢复了模型可访问性。修复前本轮检查已看到BTC、ETH恢复发布，但同时仍有上述模型拒绝、超时与旧输入过期循环，二者不能混为一个问题。

## 本轮处理方式

- 失败的旧任务、旧冻结输入、旧评分和已发布事实保留。对于已冻结的预测分析，不再等待后重跑同一输入；旧任务记录真实错误，新任务承接一次自动重试，沿用原60秒退避，到真正执行时重新获取和冻结行情。一次自动重试链通常包含初次分析及一次新输入分析；第二次仍失败就保留具体失败并通知，不继续盲重试。独立新行情事件仍可按原调度发起新分析，不把“两次”解释为该币种永久停机。
- 失败收尾、新任务创建和必要的失败通知入队在同一受授权/lease/fence校验的数据库事务中完成。创建失败则一起回滚，避免旧任务已经结束却没有后续任务的空档；外部模型、行情和消息发送仍在事务外。
- 同一引擎/币种/周期的未冻结任务合并，已有新任务可承接更新，避免重复分析。承接关系（包括复用已有任务）追加可信审计关联。对旧队列，只有已有更新且仍ACTIVE、未过期、数据OK的预测，其冻结时点覆盖旧请求创建时间，才将旧请求明确标记SKIPPED/ANALYSIS_SUPERSEDED；父任务还要确认当前子集合/持仓版本一致。不会伪装成该任务已发布，也不跳过实际的新上下文。新任务保留analysis_retry_of与次数，便于追溯；显式任务截止时间不延长。已经冻结的预测复盘仍按其历史as_of重试，不套用行情刷新逻辑。
- 子周期等待超过5分钟后，与父综合同档按等待时间取下一个模型时隙，防止父任务连续占用造成饿死。平时仍先父综合，确定性执行/验证及已授权主控请求仍更高优先。5分钟是必要的调度默认选择（已超过两次120秒模型预算），不是预测期限、交易门槛或新的风险参数，也不承诺固定完成SLA。
- 正式提交被API拒绝时，追加一条仅含错误码与任务/尝试/请求标识的可信审计事实；执行器优先报告该原因。发布已经成功时仍以数据库正式事实为准，不会被清理错误或旧拒绝记录改判失败。不从模型stdout判断成功或根因。
- 返回安全的字段路径和固定错误类型，模型能知道具体哪个字段不符合契约。拒绝请求的值、任意额外字段名、原始私有响应都不回显。插件还按本任务只读schema再次过滤提示。
- 模型上下文增加从原冻结事实派生的精确引用索引，包括本次证据ID、边界/容差、期限规则、子预测ID和有效持仓ID。程序不代填方向、目标、概率或交易动作，也不自动改模型提交的payload；所有原有验证继续执行。
- 父综合遇到明确的分钟行情缺口，先进入AWAITING_DATA，5秒后检查补齐，再冻结输入及启动模型。期间行情验证与持仓风险监测独立继续，不将缺失数据当作OK。只是监测游标和更新时间变化不作废父分析；持仓revision/数量/状态/结构绑定、子预测状态等业务变化继续严格校验。


- 对分析途中才出现的分钟核验缺口，父提交最多等待4秒，仅等待本次已引用、仍为当前head且ACTIVE未到期的子预测；每次重查授权/期限，等待发生在数据库事务外。补齐后仍执行原完整校验，真正失效或替换绝不放行；未补齐明确返回MINUTE_DATA_PENDING，模型可在原预算内重提。该等待不是延长行情或模型时限。
- 补齐发布与失败收尾的并发边界：取得任务锁后再查一次正式发布事实。如果提交刚好在失败检查期间成功，以已提交事实收尾成功，不另建重试或误发失败；此边界由真实PG并发测试验证，不宣称线上曾确认触发。

## 实施范围和边界

必要配套涉及预测输入/重试调度、可信提交诊断、安全字段提示及上下文引用展示。没有新增模型角色、订单入口、代理服务、数据库表或迁移，没有更改通知重投策略。唯一业务runtime仍为`trading-agent/`，主控Gateway与两个Hermes Profile保留。

原有180秒新鲜度、90/120秒模型预算、子Agent轮数、风险限制、真实止损止盈、到期不强制平仓等规则不变。没有通过延长期限、放宽验证、伪造结果或修改历史任务来“提高成功率”。模型仍可能超时、给出不合格报告或遇到真实上下文变化；本轮修复的是确定性重试缺陷、误触发和可定位/可恢复能力，不承诺模型永不出错或策略盈利。

程序/提示词和Profile的预测引擎身份保持不变，只因研究插件的安全提示改动更新部署锁中的插件指纹；不切换有持仓账户的引擎。原20项认证/网络/风险保护文件与现有代理配置不应变化。只应用到既有paper服务，不启用实盘或调用真实订单。

针对本轮缺陷的重要断言：

- 分析失败30秒后，再等60秒，旧任务以原错误结束，新任务有不同输入ID与冻结时点，能够通过严格校验正式发布；原输入不被覆盖。
- 第二次失败不再安排同一旧输入重跑；错误保留，正常故障通知仍保留。
- 新任务创建失败时，旧任务收尾同时回滚；已撤销/过期尝试不能写入诊断或排新任务；显式deadline不延长。
- API坏字段/错误引用不产生预测，安全提示不泄露提交值或私有字段，模型纠正后可发布；可信拒绝不会被普通stdout掩盖，正式发布优先。
- 已知分钟缺口时不抓行情/不冻结/不启动综合，5秒后补齐可继续；同范围事件不重复排队。
- 仅持仓监测时间前进不改变父决策版本，实际revision改变仍使版本不同；已平仓记录不作为当前持仓，也不因此生成新交易意图。
- 已有更新有效预测覆盖旧请求时，父/子重复请求不会调用行情或模型；子集合真正改变时，旧父请求仍重新分析。
- 等待过久子周期先于新父任务获得时隙，但确定性监测和已授权主控请求仍在前面。
