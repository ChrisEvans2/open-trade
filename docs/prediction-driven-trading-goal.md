### 3.2 三层职责

| 层 | 已确认的职责 |
| --- | --- |
| 各周期预测 Agent | 识别结构与阶段，判断走势和概率，给出触发条件、目标区间、失效条件与期限；检索经验改善分析 |
| 父 Agent | 综合各周期仍有效的结果及周期关系，自主决定开多、开空、观望，或在预测失效/转向时提出平仓 |
| 确定性程序与执行模块 | 校验信号、现有交易条件与风险限制，计算仓位、杠杆、止损止盈，按现有执行流程处理订单、成交和异常 |

父 Agent 的结果是直接驱动交易的信号。用户没有另行指定固定概率准入门槛，并已明确把是否入场交由父 Agent 判断。不得擅自增加另一个方向裁决 Agent、固定概率门槛或必须由旧技术策略先给出入场信号的门槛，取代父 Agent 的决策。概率应成为父 Agent 的判断依据和后续校准对象。

这不取消现有确定性风控、结构触发条件验证、预测有效性校验、去重或执行检查。父 Agent 无权扩大风险上限、直接调用订单工具或自行决定超出程序规则的仓位和杠杆。

### 3.3 沿用现有交易规则

- 沿用本仓库目前的确定性风控与执行规则，包括依据可承受最大损失、杠杆等计算仓位及止损止盈的流程，以及趋势单与震荡单不同的倍率、止损止盈设置。
- 先核对现有代码实际如何计算这些值，再进行接入；不能把讨论中的描述当作现有代码已实现的证据，也不能退回统一固定止损止盈的简化方案。
- 预测信号替换或接管旧入场方向来源；保留仍适用的交易风控与执行规则。若原技术策略代码同时承担参数计算，应拆分并复用必要计算，不能因为删除旧信号来源而丢失这部分规则。
- 预测目标区间和实际订单止盈价分别记录。前者用于分析交易空间、检验预测和提供父 Agent 决策依据；实际订单的风险参数仍由现有规则计算。两者如何衔接须在实现决策中解释，不能偷偷用预测目标覆盖现有止盈算法。

## 4. 结构必须是核心输入

结构不能只作为一句解释文字。需要进入预测的结构化输出、验证机制、父 Agent 上下文、案例记录和知识检索条件。

至少覆盖本轮讨论涉及的：

- 上升三角（用户称“上三角”）。
- W 底。
- 箱体与三角收敛情景。
- 相关支撑、阻力及突破/回踩行为。

每次分析应明确：

1. 形态名称、所属周期与识别依据。
2. 所处阶段：例如形成中、等待突破、突破待确认、突破确认、回踩、失效。
3. 关键价位或边界：例如三角上沿与上升下沿、W 底颈线与低点、箱体上下沿。斜线边界需要可按时间计算的位置，不应冻结成永久不变的水平线。
4. 各情景的触发/确认条件，以及目标价格区间和预测幅度。
5. 结构失效条件、价位容差与预测期限。
6. 当前证据支持程度、冲突和未知项。

W 底形成中与突破颈线后回踩站稳属于不同阶段，应能够检索对应案例。不能把所有 W 底或所有三角形套用同一条经验。

结构识别的算法、几何特征、容差和 Agent 分工尚未被用户指定，由开发 Agent 选择并说明；必要的数值计算可交给程序，分析解释交给 Agent。必须让程序能验证冻结的关键条件。证据不足时允许未知或多个候选结构，不能硬凑形态。

## 5. 趋势预测与独立生命周期

### 5.1 预测内容与概率语义

各周期至少需要表达：走势方向及概率、结构/阶段、情景触发条件、目标价格区间、失效条件、发布时点、截止时点、预测期限规则版本、引用证据。

可表达“若突破箱体上沿，上行情景目标为 A–B；若跌破下沿，下行情景目标为 C–D”，并记录各情景概率和失效条件。父 Agent 的综合预测也应有自己的目标、失效条件与期限，并引用子预测。

用户要知道的是一段趋势可能涨到哪里、跌到哪里以及何时失效。到期收盘价、期间最高/最低价、方向判断和目标触达是不同的验证对象，不能混用。

技术实现必须明确每个概率字段对应的事件、是条件概率还是无条件概率、何时开始计时、如何评分。不得把趋势强度当涨幅、把分类阈值当目标价、把条件概率和无条件概率直接相加。这些概率的具体字段设计和计算/校准方法由开发 Agent 决定并写明，不得宣称本轮已由用户指定。

### 5.2 各周期独立更新

- 各周期分别维护自己的预测和验证生命周期。
- 程序持续检查行情与冻结条件，模型只在需要重新分析时运行。不能仍然强制所有周期每小时重做预测。
- 目标达成、结构失效、期限到达是预测结束条件；到期未决单独记录。
- 一个周期得到验证结果或预测失效/到期，需要时更新该周期，无需等待其他周期全部结束。
- 任何周期产生新结果后，父 Agent 应结合其他周期仍有效的预测重新综合。
- 旧预测只有仍有效才可复用；已经失效或过期的预测退出父 Agent 的有效预测上下文，并触发必要更新。
- 父 Agent 需要解释周期关系，例如大周期上涨而小周期下跌是回调还是转向，结合结构和关键价位判断，不能机械平均概率或照抄 1h 输出。
- 在同一周期预测仍有效时，行情出现需要修订判断的新事实，可以追加新版并注明替代关系；不得改写原预测以规避失败。

### 5.3 事件验证与评分

- **趋势方向与边界准确度分别评分**；目标触达、目标区间误差/覆盖情况及结构表现也要有可核验记录。
- 先触发约定失效条件、后来才到目标，原预测应记录失效，不能倒算成功。
- 支撑阻力验证不能只检查价格经过附近，还要检查预测时约定的支撑、受阻或突破行为；“附近”的容差与行为规则提前冻结。
- 用可获得的行情粒度确定事件顺序。同一根 OHLC 同时触及目标与失效位且无法知道先后时，明确记录无法判定；不能默认有利路径。
- 记录触发/达成/失效/到期的时间和耗时、实际价格路径证据、目标是否触达、幅度误差、区间表现及可用时点。
- 案例、评分和统计按币种、周期、结构、阶段和规则版本组织；失败和到期未决不得从统计中消失。
- BTC/ETH、不同合约、不同周期、不同版本的预测不能交叉误用。回放和学习只能使用当时已经可用的数据及经验。

### 5.4 预测结束与已有仓位的关系

用户明确确认：

| 事件 | 交易行为 |
| --- | --- |
| 父 Agent 的交易预测失效 | 提出平仓，由程序校验并交现有执行模块处理 |
| 父 Agent 综合判断转向，与已有仓位方向相反 | 提出平仓；不能未经现有规则允许就同时反手开仓 |
| 预测期限到达 | **继续持仓；到期本身不触发平仓** |
| 现有止损、止盈或其他退出条件触发 | 继续按现有规则处理 |

单个子周期转向是父 Agent 的综合输入，不等于所有持仓都立即平仓。没有持仓时不得生成无意义的平仓订单。

预测到期后不得继续作为有效新开仓依据，但也不能因退出父 Agent 上下文而停止已有仓位的止损止盈或必要结构风险监测。如何衔接原持仓结构条件和新综合预测，由开发 Agent 明确设计并记录。持仓的原预测评分保持原样，不能通过延长预测期限改变历史评价。

## 6. 知识经验库：知识点—案例—操作指引

### 6.1 用户要的组织方式

经验库像题库：看到当前行情问题，先想到相关知识点，再看该知识点的具体例子和处理步骤，帮助 Agent 迅速知道该检查什么、如何分析。

| 层 | 存储内容 | 用途 |
| --- | --- | --- |
| 知识点 summary | 从多个案例归纳的认识、适用条件、误判、局限及证据状态 | 首先检索，识别当前问题涉及哪些知识点 |
| 案例 content | 支持或反驳知识点的具体预测；当时结构、证据、过程、结果与耗时，包含成功、失败和未决 | 按需展开，理解为什么成立或不成立 |
| 操作指引 procedure | 遇到该知识点应检查什么、按什么顺序分析、怎样验证 | 指导当前预测或复盘任务 |

- summary 的主体是知识点，不能再次变成某次历史迭代标题的截断摘要。
- 一个知识点可以关联多个正反案例；一个案例可以支持或反驳多个知识点。
- 操作指引与认识职责不同，应独立维护并关联知识点；可以放在同一经验库中，不必另建数据库。
- 读取流程为：识别问题 → 检索知识点摘要 → 必要时展开案例 → 读取当前任务的操作指引。
- 明确区分已获案例支持的认识、证据不足的假设、反例和失效/退役知识；不得把 Agent 自述自动当作已验证事实。
- 检索需要考虑币种、分析周期、结构、阶段和适用条件；经验跨币种复用必须说明适用性。

### 6.2 存储与接入

- 保留用户要求的独立 **SQLite / FTS5、summary 搜索、content 按需展开** 方向，重构其内容组织与服务对象。
- 可以复用当前检索、分页、版本、冻结引用等有用机制；不能保留“仅策略迭代 Agent 可访问”的权限限制，使预测 Agent 无法实际使用。
- 正式预测事实、结算和交易仍按现有 PostgreSQL 架构保存。SQLite 保存知识与关联案例的索引/内容或相应引用，不得形成两个可以独立改写同一预测结果的事实源。
- 必须说明 PG 与 SQLite 的事实归属、同步方式、失败恢复及引用一致性；跨库操作不能假装拥有单一数据库事务的原子性。
- 一次预测所见知识版本及展开案例需要可追溯；后续学习或纠错不改变旧预测引用的经验内容。
- 正式预测的同周期/同 engine 旧案例检索要与新的知识库整合，避免继续硬编码“仅一小时已结算案例”，也避免重复注入相同事实。
- 不要求新增向量库、外部知识服务或网页知识自动采集。若开发 Agent 因必要性新增此类能力，必须列入额外功能说明并解释理由。

### 6.3 移除误解产生的策略迭代库

- 删除/停用面向策略源码自动迭代的 Agent、工具、提示词、调度和对应历史迭代经验索引功能，清理活跃入口与文档。
- 复用通用检索底座不等于继续把历史策略补丁当作预测知识点。
- 删除旧派生库前确认其只服务被移除的模块；已有审计、成交事实、原始策略历史和冻结证据应保留可追溯记录，不要把“删记忆库”扩展成删除原始交易历史。
- 当前策略迭代角色删除后，**预测复盘与学习必须保留**。不得把两者一起删除。

## 7. 预测复盘、知识更新与期限学习

### 7.1 保留预测学习职责

程序记录事实与结果；预测复盘 Agent 依据多个真实案例归纳知识点、适用条件、反例和操作步骤，提出可验证调整。预测 Agent 利用这些经验改进后续分析。

具体职责可由现有预测复盘 Agent 承担或做必要拆分，但不应恢复成自动改交易策略源码的 Agent。新增角色、调度或权限时必须说明。

支持知识点新增、更新，以及有必要的合并/纠错与版本保留；每次总结引用案例，记录证据范围。没有样本时使用明确标注的初始知识/假设，不能编造成功经验。

### 7.2 期限是可学习参数

- 各周期、结构/阶段可逐渐学得不同期限，不把所有预测强行设为相同时间。
- 经验事实和当前生效的期限规则分开保存。
- 程序记录周期、结构、目标、失效边界、原期限、实际达成/失效/到期结果与耗时。
- Agent 基于引用案例提出调整，程序通过历史回放与后续影子验证检验，在满足预设标准后自动生效，并保留版本和回滚能力。
- 样本不足、验证失败或不满足规则时继续默认值；候选不能因为 Agent 自称更好就生效。
- 修改只影响新预测，已发布预测、期限和历史评分保持原样。
- 同时考察兑现率、失效率、到期未决和等待时间，避免靠不断延长期限抬高命中率。
- 学习默认不改变用户的风险上限、杠杆上限或交易止损止盈规则。

初始期限、上下限、样本门槛、回放/影子验证标准、学习频率和回滚触发条件尚未讨论，由开发 Agent 制定有界、可配置的初始方案并记录。不能把任意初始值包装成已经从案例学得的结论。

## 8. 用户不在电脑前时的决策方式

1. 用户接下来无法回答问题，不要反复发问或等待确认来解决常规技术选择。
2. 根据本文件、当前代码和现有规范自主完成必要本地实现；所有未讨论的技术选择进入决策记录。
3. 优先复用现有行情、量化、风险、执行、任务与审计机制；新组件须有具体必要性。
4. 保留已确认的业务语义。不能因实现困难退回下一根 K 线预测、历史迭代日志库或固定概率裁决。
5. 对确实依赖缺失外部资源的部分，先完成可完成的本地工作和接入代码，明确记录限制。不得伪造外部验证、绕过权限或把模拟结果写成已上线。
6. 不自行扩大到服务器部署、实际下单、启用实盘、修改凭据、提高风控上限、删除原始数据。不存在用户回复时也不得将等待时间当作这些行动的批准。
7. 每项新增机制按以下身份登记：用户明确要求的功能、实现该功能必要的技术配套、开发 Agent 自行增加的功能。三类都要在交付说明出现。
8. 开发沟通保持简短，详细过程写入文件。最终答复提供短摘要和完整文档链接，避免大量信息淹没用户注意力。
