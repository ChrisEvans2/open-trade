# 当前问题记录：证据不足时，把局部代码推断成完整架构

日期：2026-11-04。本文保留通用的调用链核查与解释要求，不公开个人对话原文。

**核心问题：AI 没有核对完整调用链，就把局部代码推断写成确定事实；用户追问时，又沿用原有解释。问题涉及事实判断，不能只归结为措辞难懂。**

## 需要核对的问题

应核对整轮分析与普通任务的超时边界、父会话与子会话的创建方式，以及任务范围由谁决定。

## 回答出了什么问题

- 使用“整轮协调进程”，没有先说明它就是本轮预测父会话所在的 Hermes 进程，使协调职责听起来像新增的独立组件。
- 混淆父会话启动与父综合阶段开始。父会话此前已经运行并调用分析工具；子结果齐备后开始的是综合阶段。不能将两者都称为“父 Agent 启动”。
- 先用“容易误导”概括上述问题，弱化了其中的事实判断错误。
- 用“漏改代码”“验收没发现”“整轮测试替换底层实现”等笼统说法解释原因，没有立即指出冲突的规则、具体测试和替换范围，导致用户反复追问。

## 核对代码后确认的实际行为

1. 唯一交易业务 runtime 为本轮任务启动预测 Hermes 父会话。
2. 父 Agent 调用 `timeframes_analyze` 工具。
3. 业务程序判断哪些周期需要更新、哪些有效结果可以复用；工具通过 Hermes 原生子 Agent 生命周期接口启动所需子会话。
4. 所需结果齐备后，工具返回父综合输入，已有父会话继续分析并提交结论。

创建子 Agent 的能力复用了 Hermes；需要更新的周期范围由业务规则约束。应分别说明“谁提出调用”“谁决定任务范围”“谁实际创建子会话”。

## 本轮能确认的原因

- **查证范围没有跟随问题扩大。**最初核对运行器和超时检查；问题转向父子 Agent 的实际运行机制后，仍沿用局部信息，直到后续才检查 Hermes 插件。
- **用代码名称替代行为核实。**没有先对应清楚任务、进程、会话和分析阶段，就用内部名称解释架构。
- **未查证的推断使用了确定口吻。**后续回答继续沿用原有前提，没有及时返回关键入口检验结论。

这些是本轮可观察到的核查与回答问题；没有证据将其进一步归因为模型底层、运行框架或上下文长度，也不能仅凭描述混乱断定项目架构混乱。

## 后续回答要求

- 解释运行机制前，核对实际入口、调用者、执行接口和结果返回路径；局部代码不足以支撑完整结论时，明确说明尚未确认的部分。
- 先说现有组件分别做什么，再引入内部术语；职责名称不能被说成新增组件。
- 明确区分会话创建、阶段开始和模型执行计时。
- 用户追问暴露矛盾时，重新检验原结论；发现事实错误就明确纠正，不只改写措辞。
- 解释测试范围时，指出具体用例、被替换的依赖及未覆盖行为；局部测试通过不能据此宣称完整链路已验证。
