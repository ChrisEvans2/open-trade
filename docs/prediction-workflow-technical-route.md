# 预测工作流技术路线与实施记录

指导文件：[预测工作流改造讨论稿](prediction-workflow-discussion.md)。

实现与验收记录日期：2026-10-26。文档表达修订日期：2026-10-27（Asia/Shanghai）。

当前记录的完成范围：本地实现和第11节所列验证已经完成；线上迁移、业务服务重启和真实模型负载验收尚未执行。本次修订只调整文档表达，不修改代码，也不重新执行业务验收。

## 1. 要完成什么，哪些限制保持不变

这次改造覆盖完整的预测工作流：由程序绑定身份，模型选择业务证据；按固定窗口合并更新需求；父Agent并行组织所需子Agent，复用其余有效结果；用明确的时间和次数上限结束失败；让预测和复盘共享两个沙箱名额。

完成标准还包括并发正确性、资源回收、错误状态和验证。仅调整并发数、停止通知，或继续沿用各周期独立排队的旧流程，都不算完成本次改造。

关键参数如下。后文说明各参数在什么阶段生效。

| 限制 | 已确认的规则 |
| --- | --- |
| 更新事件归并窗口 | 同一币种固定30秒，从首次确认事件开始计时，后续事件不延长窗口 |
| 子Agent并发 | 最多4个周期同时分析；需要更新几个，就启动几个 |
| 分析执行时间 | 父综合和每个子Agent分别最多120秒；父等待子结果不占父综合执行时间 |
| 单次模型阶段 | 父、子分别最多150秒 |
| 冻结输入年龄 | 本次分析的输入最多210秒；有效旧子预测的复用规则见第5节 |
| 正常分析重试 | 每个角色首次执行之外最多重试2次，即最多3次尝试；正常退避为5秒、15秒 |
| 整轮期限 | 实际获得资源并开始准备后，整轮最多1200秒；任务承接或重启不重新计时 |
| error后的恢复 | 最多3次，间隔为60/180/600秒；每次需要执行的角色只尝试1次 |
| 沙箱容量 | 预测和复盘共享2个名额，不为某种任务固定保留一只沙箱 |

实现阶段保留了当时已有的未提交改动。改前源码副本保存在受限本机目录`.local/private-evidence`，不复制或提交凭据。

整个过程不启用实盘、不调用真实订单、不改变风险限制，也不另起交易入口。历史预测、评分、任务和审计继续保留，新增事实采用追加方式保存。本地模拟测试与线上迁移、安装及真实模型验收分别报告。

## 2. 协调过程需要保存哪些记录

协调状态必须存入数据库。这样程序重启后，仍能知道正在处理哪一轮、哪些周期尚未完成、已经用了多少次尝试，以及资源是否已经安全回收。

本次新增向前迁移0010，不改写旧0009，也不删除或重写历史事实。原有`prediction_inputs`和`prediction_facts`中每个job对应记录的唯一性约束保持不变。

| 记录 | 用途与保存内容 |
| --- | --- |
| `analysis_scopes` | 保存同一引擎下某币种的当前协调状态，简称scope。每个引擎/币种一行，记录归并窗口、待更新周期、活动轮次、父结论可用性、错误组、恢复次数及最早恢复时间。它是当前状态的投影，不替代历史预测正文。 |
| `analysis_rounds` | 保存一轮分析的稳定身份、主协调任务（job）、首次实际开始时间、绝对截止时间、恢复序号、状态和正式父结果。任务承接不能重置这一轮的时间和次数。 |
| `analysis_runs` | 保存父Agent或某周期子Agent的一次角色尝试，包括对应job/attempt、冻结输入、执行与阶段期限、结果和错误。父、子分别使用受管理的内部job，继续复用原有不可变输入与预测事实表；这些内部job不会再被全局调度器独立领取，也不会各自触发父综合。 |
| `analysis_events` | 追加保存更新、错误及恢复过程的事实，按真实来源键去重。归并只合并待处理周期，不删除原始事件。 |
| `model_slots` | 保存两个模型沙箱名额的占用与清理状态，并通过attempt关联运行归属。清理结果未知时保留并隔离该名额，不能仅凭租约过期就认定沙箱已销毁。 |

新增事实表继续使用禁止`UPDATE/DELETE/TRUNCATE`的触发器。应用账号对新表的权限，由原有`provision/verify`流程配置和验证。

每次角色写入都在同一事务内检查：协调attempt是否仍获授权、租约（lease）是否有效、执行代次凭据（fence）是否匹配、是否在期限内，以及角色绑定是否正确。迁移已在独立真实PostgreSQL中测试，业务库不会随本地实现自动升级。

## 3. 如何合并变化、启动任务和分配名额

同一引擎下，同一币种同一时间只运行一轮分析。父Agent仅为没有可用预测的周期启动子Agent；需要更新多个周期时并行执行，其余复用有效预测，结果齐全后统一综合。分析期间经确认、需要更新预测的变化归入当前轮次，在准备输入和提交结论前核验，不因单次变化或单个子结果发布而另建父任务。

### 固定30秒窗口

达到目标、结构失效或预测到期，经程序确认后才进入更新集合。首个事件打开30秒窗口，后续事件只增加需要更新的周期，不延长关窗时间。BTC和ETH分别计时，普通价格波动和监测进度前移不进入这个窗口。

例如，BTC的1h预测先失效，18秒后4h也确认需要更新，两者在第30秒一起进入分析；6h和12h仍有效就直接复用。即使执行器在第30秒之后才领取任务，后到的事件也不能继续推迟已经到期的窗口。

失效标记和已有持仓保护立即执行，不等待30秒窗口结束。同一引擎/币种的状态变更，由现有PostgreSQL事务锁按顺序处理，避免同时产生互相冲突的更新。

### 两个名额如何领取

任务领取和沙箱名额预留在同一事务完成。没有空闲名额时，任务继续等待，不提前消耗attempt次数或冻结行情。同一币种的轮次不能竞争发布。

确定性验证和交易执行保持独立、优先运行，不占模型沙箱名额。预测与复盘都可以使用任一空闲名额；等待过久的任务按已有等待补偿规则获得执行机会，不固定专用沙箱。

### 如何处理同时发生的操作

“竞态”指多个操作发生时间接近，其先后顺序可能影响结果。例如，结构失效可能与结论提交同时发生，进程也可能在发布成功后报错退出。

因此，事实发布、版本检查和可用性检查必须放在同一个受保护事务里。外部I/O不放入该事务。验证需要覆盖重复事件、第30秒边界、并发领取、失效与提交同时发生、旧fence回写、发布与失败收尾竞争、重启恢复，以及清理结果未知等情况。

## 4. 父Agent如何组织子Agent并提交结果

一轮分析由当前Hermes父会话组织，使用公共`subagent_lifecycle`启动所需角色，最多4个周期同时执行，具体选择理由见8.1。父、子在本轮中共享沙箱生命周期，但使用不同工作目录，输入保持只读。

正常流程如下：

1. 程序确定哪些周期需要更新，并从数据库读取其余仍有效的预测。
2. 为需要分析的周期准备并冻结输入，准备好一个就启动一个子Agent，让模型分析与后续行情准备重叠。
3. 子结果可以按不同顺序返回；程序逐个校验、保存，当前父会话继续等待尚未完成的必要结果。
4. 所需结果全部完整、有效后，重新冻结父自己的行情，再开始父综合。
5. 父提交结论时，程序再次核验依赖和授权条件，通过后才正式发布。

等待子结果不消耗父综合的120秒执行预算，但准备、等待、协调和重试仍受整轮1200秒期限约束。外层runner负责监督阶段与整轮期限、续期，避免用旧的90/120秒整进程限制提前终止仍在等待子结果的父会话。

### 哪些身份由程序绑定

新增的轮次状态、角色准备、失败和提交接口，都受任务令牌保护。服务端根据当前协调任务确定引擎、币种和轮次，再把角色run绑定到内部受管理attempt。

模型只提交分析内容，不填写已经确定的`job/input/position/context_revision`等身份。原有v2历史查询继续保留，正式事实仍使用`schema=3`；新的模型提交契约移除了固定身份字段，不改写历史格式。

### 哪些选择仍由模型完成

结构、期限规则、知识和子预测证据具有业务含义，仍由模型选择。工具为这些选择提供本次输入内、有类型的短引用；映射来自不可变的冻结输入，不按“当前最新同名对象”猜测替换。

父实际采用的完整子结果集合由程序记录，模型实际选择引用哪些证据则另行保存。即使某条反向信息未被引用，也不能因此退出依赖核验。

原生遥测、父阶段开始与结束、子耗时、重试序号和正式提交分别记录。是否发布成功以正式保存的事实为准，不根据stdout判断。

## 5. 失败后重做哪些角色，何时必须停止

正常重试和error恢复使用同一套范围判断：先重新获取所需行情并逐角色核验，再决定需要重新分析哪些角色。

| 当前情况 | 处理方式 |
| --- | --- |
| 四周期都没有可用结果 | 四个子Agent并行分析 |
| 只有部分周期不可用 | 只更新这些周期，其余有效结果复用 |
| 只有父综合失败 | 重新冻结父输入，只重试父综合 |
| 父重试前，又发现子依赖失效 | 先补齐受影响的子周期，再综合 |

复用旧子预测时，检查的是它现在是否仍有效，不要求它当初的冻结行情年龄也小于210秒。新分析自己的冻结输入，仍严格受210秒限制。

### 正常重试不重置轮次

某个角色已经执行过，后来因结构失效、输入过期或技术错误再次分析，就消耗该角色的剩余尝试次数。仅登记事件、合并需求或等待，不消耗分析次数。

每次重试创建新的受管理job并重新冻结输入，旧事实继续保留。角色计数和整轮截止时间不会因为job ID变化、任务承接或进程重启而重新计算。正常两次重试分别退避5秒、15秒；30秒归并窗口也不能不断叠加成无限等待。

### error恢复有独立的上限

一轮分析以error结束后，最多再提供3次恢复机会，间隔为60/180/600秒。每次恢复只让当时需要执行的角色尝试1次，不再嵌套正常阶段的2次重试。恢复次数归属同一个稳定错误组，持续保存。

恢复等待期间，如果又确认其他周期需要更新，只扩大待处理集合，保留原恢复时间、错误组和次数。退避时可以释放已确认清理的名额；恢复次数耗尽后，普通调度tick不能重新开启无限恢复。只有错误组已结束之后的独立业务事件，才允许建立新的正常轮。

### 结构失效与数据缺口分别处理

程序使用完整、已收盘的分钟数据核验预测已声明的失效条件，保留原来的确认bar数和容差。父预测有自己的独立情景；即使所有子预测仍有效，也可以单独核验父预测。

普通价格波动不构成结构失效。分钟数据有缺口时，状态是“待核验”，先在原预算内有界等待和补齐；不能恢复才明确结束为error。分析期间的条件核验与发布后的评分窗口分开处理，不改写历史评分起点。

一旦出现错误，旧父结论立即停止作为当前决策依据，并保留具体label和审计记录。技术故障不写成市场`INVALIDATED`，避免误触发平仓。只有完整、有效的新父结论正式提交成功后，才恢复当前可用性。

## 6. 如何验证改造符合这些规则

验证按顺序进行：先检查独立PostgreSQL迁移和提交契约，再测试轮次、并发及事务一致性，随后运行固定Hermes原生插件测试，以及执行风控、主控查询与通知、授权和资源恢复回归。

时间边界使用确定性时间推进来测试，覆盖30秒窗口、210秒输入年龄、120/150/1200秒期限和60/180/600秒恢复，不要求每个用例实际等待完整时长。

| 验收方向 | 必须满足的行为 |
| --- | --- |
| 身份与证据 | 不混用ID；角色与引用不能越权，程序不猜测纠错 |
| 子Agent协调 | 所需四子确实并行；乱序完成后只综合一次；单周期或父自身重试不带跑有效角色 |
| 行情变化 | 分析、重试和提交期间都能检出真实结构变化；普通波动不触发重做 |
| 错误出口 | 不把旧父结论作为成功备用结果；恢复次数跨重启保留，耗尽后停止 |
| 两个沙箱名额 | 不超发名额，复盘能获得空位；清理未知的资源不提前释放 |
| 授权与事务 | 旧owner/fence不能写入；外部I/O不进入数据库事务；关键检查与事实保存一起提交 |
| 历史与兼容 | 历史事实仍可读取，正式预测、评分和审计不被覆盖 |

本地测试不启用实盘或触发真实订单。真实Cube双沙箱容量已有历史证据，但新工作流中两个真实模型、8个子Agent同时执行的负载仍需单列验收。

交付记录包括实际文件范围、验证命令、通过与失败结果、已知限制、回退方式和证据位置，并同步更新Feature.md。未提交的工作不归档到changelog，也不声称已经提交。

## 8. 实际采用的技术方法

### 8.1 原生并行与角色绑定

实现采用固定Hermes提供的公共`ctx.subagent_lifecycle`。它允许分别启动子Agent、逐个读取结果、持有取消句柄，并监督各角色实际经过的时间，也就是墙钟时间。传统`delegate_task`同步批次的超时包含“无进展”判断，不能直接作为120秒硬限。本次没有修改固定Hermes源码。

行情准备依次进行，准备好一个角色就立即启动其原生子Agent，不等待前一个分析结束。这既让模型执行与后续准备重叠，也避免四次各80根K线的冻结事务同时争抢协调任务锁。四子同时运行已通过原生公共生命周期加模拟传输（fixture）的测试；真实耗时仍取决于行情准备和真实模型。

公共生命周期不使用传统委派的`max_iterations=6`配置。因此，不能把旧Profile中的6轮当作新接口的限制；本实现通过服务端角色期限、插件墙钟和宿主监督，共同执行120/150秒限制。单会话允许的子任务总数需要容纳受次数上限约束的重试，但同时运行的子Agent仍最多4个。

公共结果也不包含传统批次完整的`truncated`元数据。原生状态和正式发布状态分别记录；即使原生返回`SUCCEEDED`，结果仍必须通过严格JSON和领域校验，才能算正式预测成功。

每次启动子Agent时，启动钩子将原生session绑定到程序创建的run，子工具自动携带该绑定。父开始综合后，绑定自己的run。模型不能选择任务、输入、币种身份、真实持仓或上下文版本；真实数据库身份保存在原有`schema=3`正式事实中。

原生启动上下文还有32k字符限制。输入超过安全余量时，启动信息会明确要求子Agent调用已经绑定角色的`research_context`，读取完整冻结输入，不通过截断来省略证据。

### 8.2 每次重试都重新核验依赖

复用预测不能只看数据库里先前保存的OK状态。开始角色分析和父提交前，程序还会检查：当前预测是否已经核验到最新已收盘分钟。

如果核验进度落后，就调用同一个确定性验证器补齐行情、核验条件并追加事实。这项调用由服务内部显式授权，不新增允许模型自由提交验证数据的接口。原有独立确定性监测任务继续运行，所有行情请求都在事务外完成；分钟游标发生竞争时，允许重新读取一次，真实数据缺口仍按待补齐处理。

对于尚未发布的草稿，程序另行检查冻结之后完整分钟内的声明失效条件。父发布时，还会在同一事务重新检查四周期完整性、待更新集合、当前版本、持仓和角色期限。任一条件不满足，整笔事实、交易意图和状态变更一起回滚。

正式评分仍从原有发布后观察窗口开始，不因草稿核验而改变历史评分窗口。已到期归并窗口不续期，error等待中的新变化不重置恢复上限，具体规则见第3、5节。

### 8.3 超时、发布与崩溃如何确定处理顺序

每个角色都保存准备开始、执行开始、执行完成确认、发布或失败收尾时间，以及执行和阶段两层截止时间。

角色从`RUNNING`进入`SUBMITTING`，表示分析执行完成、开始提交。这个状态转换必须在同一事务内检查期限，不能先检查有效、等超时后再确认完成。重启回收也会处理`SUBMITTING`，避免遗留仍可写入的角色。

父提交失败后，插件结束该角色，宿主中断本次父会话，再用新输入重试。不能在已经宣布执行完成之后，继续无限模型分析。

同一个宿主attempt可能先后启动多个原生会话，程序用`launch_index`区分它们。这样，旧会话的失败不会提前终止下一会话，具体失败原因也不会被后续通用超时覆盖。

如果正式父结果已经提交成功，后到的进程退出或清理报错不能把它改判为发布失败。如果父结果尚未发布，协调任务又已失去执行能力并超过1200秒，恢复器会关闭轮次、撤销未完成角色、记录error，并安排有界恢复。领取函数不能只把任务标成旧式`SKIPPED`，却留下永远占用的scope。

### 8.4 两个名额如何回收，取消影响多大范围

任务领取与`model_slots`预留同时提交。清理未确认时，名额保持隔离；旧attempt还占用资源时，不能仅因租约过期就领取同一job的新副本。重启后，先扫描并清理归属匹配的沙箱、回收已确认的进程，再释放名额。

父、子根据task身份的哈希值使用独立工作目录，输入只读。这可以避免工作文件互相覆盖，但不代表同一UID的子Agent之间多出了一层安全隔离。

取消单个终端命令时，在该命令的随机目录写入取消标记，由命令监督器停止自己的进程组，不直接销毁整个共享沙箱。监督器通过Linux `waitid(WNOWAIT)`观察退出，并在取消完成前保留子PID，防止PID被复用后误杀其他进程。宿主仍负责最终清理整只沙箱。

取消未确认时，不启动替换子Agent。具体边界如下：

| 情况 | 处理方式 |
| --- | --- |
| 原生超时取消在3秒内仍未确认 | 插件报告取消未确认；宿主结束本次进程，清理整只沙箱后再重试 |
| 子任务未收到完成确认 | 宿主同时检查子期限，最多给予5秒清理余量；不延长服务端120秒发布授权或150秒阶段期限 |
| 整只沙箱因异常被回收 | 其他尚未形成事实的子也可能被中断；已经发布且仍有效的结果继续复用 |

### 8.5 如何查看可用性、错误和耗时

error会立即停用旧父结论。最新查询不再把它作为当前成功结论返回，开仓检查也会拒绝旧意图；按ID查询的历史记录继续保留。

已有持仓的绑定平仓仍先按原风控规则判断，不受这项开仓门禁阻断。技术error不伪造结构失效，因此不会仅因模型故障就触发结构失效平仓。

运行就绪状态（readyz）包含每币种的scope状态、具体错误、待更新集合、恢复次数和下次恢复时间。重启后从数据库恢复这些信息；其他币种或复盘任务成功，不能掩盖仍存在的error。

通知继续使用原outbox，只在一组error开始和自动恢复停止时通知，不为每次内部角色重试逐条发送消息。

耗时由不同记录分别保存：`analysis_runs`保存角色阶段时间和结果，主job保存排队与领取时间，原生usage保存子耗时。后续运行积累样本后，可以按角色、模型和成功/失败分别统计P50/P95/P99、观察峰值及超时率。

其中，`execution_finished_at`是工具确认完成的时间，不等于纯模型HTTP推理耗时。新流程目前没有真实模型耗时峰值样本；指导文件第10节的历史统计仍属于旧工作流证据。

## 10. 后续如何部署，出问题如何回退

以下是尚未执行的后续步骤。按项目AGENTS.md，服务器迁移、安装和线上验收属于后续授权阶段；原实现阶段没有启动`/srv/open-trade-deployment`的业务服务，也没有对业务数据库执行0010。

部署必须按顺序进行：

1. 停止唯一runtime，确认没有旧交易入口并行执行。
2. 备份并验证备份可恢复。
3. 在人工迁移环境运行现有`ta migrate`，迁移到0010。
4. 按原有`provision/verify`流程配置并核验新表权限。
5. 安装匹配的代码、提示词和插件，重新生成并核验部署锁和Profile hash。
6. 检查显式旧配置：并发1、90/120或180秒等值，应与本方案的并发2、120/150/210秒同步。
7. 通过doctor和隔离门禁。
8. 在允许的非实盘环境中，验收真实模型与双沙箱负载。

新代码要求数据库版本为0010，不会在旧库上静默继续旧调度。迁移不提供删除历史的downgrade。

出现问题时，先暂停新分析并保留当前全部事实，再使用匹配0010的修复版本向前恢复。备份用于灾难恢复，不能通过回灌旧备份丢弃后来已经形成的真实预测、评分或交易事实。回退过程中同样不启用实盘、不更改凭据或风险上限。
