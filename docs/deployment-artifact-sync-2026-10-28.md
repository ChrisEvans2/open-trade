## 2. 为什么要把这些东西一起同步

一套Agent系统由多种不同职责的东西组成：

| 内容 | 在系统里负责什么 |
| --- | --- |
| runtime程序 | 调度任务、绑定身份、校验结果、保存事实，调用原有确定性风控与执行 |
| 研究插件 | 把runtime提供的任务能力变成模型可以调用的工具，配合父/子角色完成分析 |
| Cube插件 | 将模型需要的终端操作接入受限制的沙箱，并管理命令与取消行为 |
| 提示词 | 向模型说明分析任务、证据要求、角色职责和输出约定 |
| Profile | 为某个Hermes角色选择模型、工具和运行设置，并隔离其凭据与上下文 |
| 部署锁 | 记录这些配置、插件、提示词及隔离报告应当组成的版本清单 |

这些部分通过约定协作。例如，新runtime会按新规则绑定角色、组织子任务和监督取消；插件必须理解相同的任务流程和提交约定，提示词也必须让模型使用相同的工具与输出方式。

只更新其中一部分，可能出现“程序要求新行为，工具仍采用旧行为”的情况。把配套产物一起生成、安装和核验，可以在调用真实模型之前检出这种不一致。

Cube插件属于Hermes到沙箱的适配层。本轮更新这个适配层，既有Cube服务端、模板和网络隔离配置保持原样，不需要因此重启Cube服务。

## 3. 部署锁如何判断版本一致

系统对插件、提示词等内容计算摘要，常用算法为SHA-256。摘要可以理解为由内容计算出来的指纹；内容变化通常会产生不同的指纹。

新部署包生成时，程序根据当前配置和源码计算一份期望清单。安装后，启动前检查重新读取实际文件，并同时核对三个方面：

1. 当前配置和源码计算出的期望值，是否与部署锁一致。
2. Profile中实际安装的插件、配置和偏好文件，是否与锁中的记录一致。
3. 真实Cube隔离报告的内容、配置关联和文件摘要，是否符合既定要求。

通过这些检查，旧插件配新清单、改过的Profile配旧清单、Cube配置变化后继续引用旧报告等情况会被拒绝。本次新锁由现有生成工具计算，没有手工修改摘要来绕过核验。

部署锁承担版本记录和一致性校验；runtime只能有一个实例运行，则由另一个数据库实例锁负责。两者的用途不同。

摘要相同能支持“这份内容与记录一致”的结论。业务流程正确性依靠测试和运行证据，预测价值还需后续观察；摘要校验本身不能证明这些效果。

## 4. 为什么先准备完整文件，最后发布清单

本轮先在新的受限目录生成部署包，保存改前文件，再验证新包内容。安装时先准备完整的新插件目录，检查可解析且内容匹配，然后替换实际插件目录，最后替换部署锁。

文件或目录的单次更名替换可以避免读到写了一半的文件。整批产物之间的一致性，还依靠“清单最后发布”和启动前重新核验来保证：如果同步中途停止，新旧内容混合，校验应明确拒绝启动。

本次整个过程中交易runtime都处于停止状态。主控bridge没有变化，原Gateway继续运行，不需要为这次预测插件文件同步重启它。

文件发布和进程运行也有先后关系。新启动的研究进程会读取已安装的新插件；已经运行的Python进程通常仍持有原来加载的模块。本轮没有对正在运行的Gateway做热更新，也没有把“文件已同步”写成“新业务流程已经运行”。

## 5. Profile隔离为什么保留

主控Hermes负责通过TG与用户交互，使用bridge查询事实和申请有界任务；独立预测Hermes负责执行预测父/子任务。两者复用同一个业务runtime，但使用不同Profile。

Profile把模型设置、工具范围、偏好和凭据分开，使每种角色获得自己需要的能力。预测模型的研究工具要结合当前任务授权使用，TG对话也保留原来的工具限制。本轮直接核对已有Profile，既然已经匹配，就保留其认证、TG配置和工具边界，减少不必要的变更。
