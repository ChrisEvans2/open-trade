# 主动成交分钟聚合：本地实现与验证（2026-11-03）

本轮按用户要求，把 CVD 和主动买卖比的默认原料切换为公开历史逐笔：长期保存分钟聚合，短期保存压缩逐笔，程序自动检测异常并重试补抓。可能存在的聚合错误已直接记入根目录 [README](../README.md#可能存在的问题逐笔成交与分钟聚合)。本轮是本地开发和测试，尚未部署、迁移业务库或启动线上采集；不代表各周期已经获得连续有效数据。

## 谁检测、谁抓取

两件事都由**确定性代码**执行。唯一交易 runtime 启动后台采集任务，按配置查询官方公开接口；它不会等预测 Agent 判断，也不需要 Agent 申请工具。预测 Agent 只看到冻结后的指标、来源和质量说明。

接口选择、分页、去重、单位换算、时间边界和校验规则写在程序中；保存时间、回补范围、重试间隔和请求预算通过配置调整。这样同一批原料可以复算和测试，异常处理不依赖模型是否注意到问题。没有新增 Agent、消息网关、订单入口或独立交易进程。

## 各模块改了什么

| 模块 | 新行为与用途 |
| --- | --- |
| 行情采集 | BTC-USDT-SWAP、ETH-USDT-SWAP 按完整分钟获取公开历史逐笔，使用交易 ID 分页；复用原 HTTP 客户端、限速与截止时间。默认不再请求已确认有问题的 Rubik 主动成交统计接口。 |
| 分钟聚合与校验 | 按官方 taker side 分买卖，合约张数乘合约面值转成币数量；普通成交和 source=1 成交均计入。以对应已收盘 1m K 线成交量核对总量，另外走独立分类复算核对买卖方向。 |
| 数据保存 | 长期分钟事实与短期逐笔缓存分开。分钟保存买卖量、笔数、成交分类、原料摘要、分页状态、对应 K 线摘要及质量；逐笔按分钟压缩，避免逐笔建立数据库行和索引。 |
| 异常补抓 | 缺页、空响应、重复 ID 内容冲突、分类不明、量不匹配、超预算等都明确缺失；任务记录原因并按退避间隔重新从官方抓取整个分钟。 |
| 历史抽查 | 默认每币每小时抽查一个已验证分钟，优先选择修复窗口内最久未检查的分钟；到期抽查优先于历史初始化，BTC/ETH 轮转，避免高成交量币种耗尽预算导致另一币种长期没有机会。 |
| 预测输入 | 在原有授权、租约、fence、期限检查事务内，只读当时可用的分钟版本，组合成 1h/4h/6h/12h 窗口供已有量化公式计算。没有在数据库事务中请求外部 API。 |
| 数据库及权限 | 新增可变采集任务表、可过期逐笔缓存表和分钟查询索引。永久事实继续追加保存。只有逐笔缓存获得 DELETE 权限，正式行情、预测、评分、审计仍禁止删除。 |

本轮只更换 CVD、主动买卖比的默认数据来源及相应采集链；此前 ETH/BTC 弱证据、固定五币市场篮子、资金费率时点与样本强平政策继续保留。

## 校验怎样发现问题

1. **合约和单位**：只接受当前配置的 BTC/ETH USDT 线性永续，核对官方合约元数据。以官方面值换算张数；同时核对 K 线张数与币数量，不能把张数直接当 BTC/ETH 数量。
2. **时间**：每个分钟取 `[开始时间, 结束时间)`，恰好在下一分钟开始的成交不计入本分钟。只使用已结束且官方标记收盘的 K 线。采集前检查本机与官方时钟偏差。
3. **分页与重复**：以时间定位第一页，随后按交易 ID 向更早的数据翻页，检查页面顺序与游标推进。相同交易去重；相同 ID 出现冲突内容则拒绝。必须翻到分钟开始之前；即使当前累加量恰好相等，空响应或未完成分页也不能视为完整。
4. **总量**：买量＋卖量与分钟 K 线币数量比较，容差为相对 `1e-6` 与绝对 `1e-8` 中较大者；不是允许几个百分点误差。零量分钟也必须有完整边界证据。
5. **方向**：聚合之外，重新按原始 `side` 筛选买卖分别求和。测试包含“把买卖反过来但总量不变”的反例。遇到未知 side/source 拒绝该分钟，不静默丢弃。
6. **补抓与修订**：异常分钟自动重试，修好后追加新分钟版本。已验证分钟的抽查遇到暂时网络或空响应失败，会另记审计而保留原有效版本；发现实际量差、分类等数据问题则追加无效版本，后续预测不再使用旧有效值冒充正常。

**仍可能存在的问题**：这些校验不能独立证明交易所原始 `side` 永远正确，也不能保证发现我们所有潜在实现错误。两条计算路径共同理解错某个字段，可能仍得到一致结果。抽查是有限样本，不是每小时重扫所有历史。README 保留这些限制，后续需持续观察与扩充方向样例。

## 保存和回补的默认值

| 设置 | 默认值及含义 |
| --- | --- |
| 原始逐笔留存 | **24 小时**，按本次采集接收时间计算；压缩缓存到期由程序删除。历史补抓新收到的原料也保留 24 小时。若 runtime 停止，清理会在恢复运行后继续。 |
| 分钟聚合留存 | 长期、追加版本。缓存过期不删除分钟结果和预测引用。BTC/ETH 的基础粒度合计每天 2,880 个分钟槽位，修订和审计另计。 |
| 初始回补 | 最近 **11 天**，覆盖 12h CVD 的 20 个周期，即 10 天，加周期边界余量。先补最近分钟，逐步向过去推进。 |
| 自动修复回溯 | 最近 **30 天**。超过窗口的待处理或错误任务标记过期，不悄悄继续无限抓取；配置允许最多 80 天。 |
| 调度间隔 | 每轮处理完后等待 **15 秒**；分钟结束后至少等 **10 秒**。这是采集资格延迟，不保证精确在第 10 秒收到数据。 |
| 每轮预算 | 最长 **40 秒**、最多 **300 次逻辑 GET**、最多处理 **12 个分钟任务**；单分钟最多 **300 页**，任一限制先到就停止。底层网络重试也受同一截止时间和共享限速约束，逻辑 GET 次数不等于真实 HTTP 尝试次数。 |
| 异常退避 | 从 **60 秒**起递增，最多 **1 小时**；待处理任务落库，重启后继续。 |
| 历史抽查 | 默认每币 **60 分钟**一次，轮换修复窗口内最久未检查的已验证分钟。 |

这几个值是本轮自主选择的运行默认值，均进入配置与引擎版本。逐分钟 REST 分页能复用同一套实时收集和历史补抓规则，且方便核对完整分钟；代价是请求量和延迟高于持续 WebSocket 推送，本轮没有新增 WebSocket 成交采集器。

初始 11 天回补有较多请求，耗时取决于成交笔数、限速与其他行情请求。市场繁忙时，单分钟可能超过整轮预算；程序会明确缺失并重试，不能保证所有分钟都在默认预算内补齐。不能以“两组分钟测试通过”推定 10 天历史、所有周期或线上持续采集已经验收。

数据库会回收过期缓存供后续写入复用，但删除缓存不等于数据库文件立即缩小；实际磁盘容量还需部署后观测 PostgreSQL 的维护和压缩效果。分钟保存是有损聚合：24 小时后，本地只能按既有分钟买卖量组合更长周期，无法重新按单笔大小等全新规则分类。官方历史仍可查时，可以重新获取明细。

## 官方补抓能恢复什么

官方历史逐笔文档说明提供最近三个月的分页查询，每页最多 100 条；本轮默认自动修复范围主动限定为 30 天。抓取使用 `/api/v5/market/history-trades`，对照使用 `/api/v5/market/history-candles`，面值使用 `/api/v5/public/instruments`。[官方历史逐笔说明](https://www.okx.com/docs-v5/en/#order-book-trading-market-data-get-trades-history)

K 线能提供成交总量，不能提供丢失成交的买卖方向。因此修复方式是重新取逐笔再聚合，不能根据 K 线差额猜买卖分配。超出官方查询范围、持续 API 异常或未来接口规则变化，仍可能无法恢复。旧 Rubik 入口为显式兼容选项，默认不使用，也不存在自动退回该接口的逻辑。

## 旧预测如何保持不变

冻结输入读的是在当时决策时点已经可用的分钟版本。每个周期聚合保存分钟版本摘要和可用时点，分钟事实本身长期保留，可按币种、时间范围和时点恢复引用集合并校验摘要。缓存不参与冻结引用。

补抓后的原料记录真实接收时间，不能假装过去已经收到。新的修订只影响之后生成的输入；已经冻结的预测再次读取仍是原输入，历史评分不回填。分钟覆盖不足时 CVD 和主动买卖比维持 `MISSING` / `PARTIAL_COVERAGE`；不能用未来补到的数据修饰过去的可用性。

## 迁移、回滚与交付边界

新增迁移 `0011_trade_minutes`，正式启动需先在授权的部署阶段迁移，并重新执行现有最小权限配置工具。运行账号只允许删除过期原始缓存；事实表仍不可修改/删除。运行健康信息增加采集任务状态、最后进展与本轮验证/缺失数量；指标缺失不自动升级为全局停机条件。

本轮未操作 `/srv/open-trade-deployment`、未启动业务 runtime/模型、未提高风险或修改凭据，也没有 commit/push。测试数据库使用隔离的 55432 端口。真实服务启停、连续数据覆盖、HTTP 负载、磁盘占用及模型使用效果仍需部署后单独验收。

回滚代码时只撤本批改动，保留之前未提交工作和已写入正式事实；数据库不执行删除事实的 downgrade。若只是停止新采集，可在受控部署中切回显式旧来源配置，但旧接口已有源端问题，不能把这个回滚选项当成可靠数据恢复方案。服务版本与迁移版本须配套，禁止在同一账户并行启动两个入口。

主要实现位置：行情采集 `market/trades.py`、`market/trade_collector.py`；分钟读取 `storage/trades.py`；表定义与权限 `storage/trade_schema.py`、`storage/permissions.py`；接入 `prediction/service.py`、`runtime/lifecycle.py`、`runtime/factory.py`。这些路径均相对 `trading-agent/src/trading_agent/`。配置见 `trading-agent/config.yaml`。
